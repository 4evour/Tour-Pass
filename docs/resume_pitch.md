# Tour Pass 简历表达草稿

## 项目名称

C++ 城市自由行结构化行程规划算法服务

## 项目描述

基于 C++17 开发面向自由行场景的城市多日行程规划算法服务作品集，使用长沙样例数据（25 个 POI 节点、46 条通勤边）将景点、餐厅、酒店和夜间活动点建模为带时间窗约束的 POI 图，结合 Dijkstra/A* 最短路、Beam Search Top-K 调度、兴趣评分、餐饮插入、候选方案生成和文本检索，为用户生成结构化旅行计划，并通过 OpenAI/DeepSeek 兼容接口或本地模板生成中文行程解释。

## 项目职责

- 设计 POI 与通勤边数据模型，将开放时间、游玩时长、兴趣标签、热度和消费水平纳入规划约束。
- 实现基于 Dijkstra 的 POI 最短通勤时间计算，并将两两最短通勤缓存改为 `auto/all_pairs/on_demand/disabled` 可配置策略：`500` POI 以内默认全量缓存，超过阈值才切换按需 LRU，避免把几百点规模过度设计成复杂缓存亮点。
- 设计多目标评分函数，综合兴趣匹配、必去景点、热度、价格、时间窗和用户节奏生成候选安排。
- 实现基于 Beam Search 的日内 Top-K 路线搜索，在上午、午餐、下午、晚餐、晚上等时间槽保留多个局部状态；规划前先做类型、时间窗、策略标签和必去点候选召回裁剪，再对小候选池评分，避免全量 POI 直接进入 Beam Search。
- 设计轻松少走路、紧凑多覆盖、文化优先、美食优先和雨天室内等候选策略，通过不同评分权重对比不同约束下的行程结果。
- 输出候选方案对比指标和站点评分拆解，将热度、兴趣、必去、通勤、价格和时间窗惩罚拆成可解释分项。
- 对候选方案进行 Pareto 非支配排序，标记评分、通勤、开放时间风险和必去覆盖之间的多目标取舍。
- 实现轻量 BM25 POI 检索，结合名称、标签、区域和描述字段权重返回匹配词与排序解释。
- 实现 LLM/模板解释层，使用内置 HTTP client 调用 OpenAI 兼容接口，并支持无 API Key 环境下稳定演示。
- 使用 `cpp-httplib` 封装本地演示 HTTP JSON API，提供 `/trip/plan`、`/poi/search`、`/route/shortest`、`/trip/alternatives`、`/itinerary/explain` 和 `/health` 等接口。
- 构建本地 Web 演示台，展示偏好输入、候选行程、路线带、每日时间轴、方案 KPI、路径耗时、替换方案和自然语言解释，便于面试现场演示。
- 输出站点级决策依据、优化前后通勤时间对比、约束命中说明和未安排原因，增强规划结果的可解释性。
- 建立 GitHub Actions 质量门禁，自动执行样例数据校验、跨平台 CMake 构建、CTest 和 API 冒烟验证。
- 建立性能回归基准脚本，支持持续时长、梯度并发、缓存绕过、吞吐量、错误率、p95/p99 和异步任务耗时统计，用于发现本地演示链路回退；不包装成生产压测结果。
- 建立高德 Web 服务真实 POI 采集流水线，支持长沙 `200+` POI 本地生成、多类别分页抓取、去重、字段标准化、manifest 报告，以及距离测量/路径规划优先的通勤边生成；正式真实数据报告用 `--fallback fail` 和 `--min-amap-ratio` 避免把估算边包装成真实路网。
- 建立规模实验脚本，支持真实/合成数据集、缓存模式、启动耗时、avg/p95/p99、失败数和 JSON 报告，用于回答“样例扩大后如何退化/优化”的面试追问。
- 建立小规模算法质量检查脚本，用 8-10 个候选 POI 精确枚举基线，并补充贪心 baseline 与 Beam Search 的同口径对比，说明近似算法有可复查口径但不承诺全局最优。
- 接入 SQLite 3.53.1 持久化规划请求、异步任务、benchmark 记录和数据版本；规划热路径仍使用内存图，数据库用于可复盘证据而非支撑高并发。

## 项目亮点

项目把图搜索、Beam Search 时间窗调度、多目标排序、Pareto 非支配排序、评分拆解、候选方案对比、性能热路径优化、CI 自动验证和 LLM/模板解释结合起来，解决自由行规划中“去哪玩、怎么排、去哪吃、时间是否够用、为什么这样排”的实际问题。当前长沙数据规模为演示样例，亮点应表述为建模、约束处理、可解释规划、规模瓶颈优化和工程验证闭环，而不是生产级旅游平台或高并发服务。

## 简历可用压缩版
