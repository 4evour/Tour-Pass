# Tour Pass 项目解释文档

这份文档面向面试复习和项目自讲，目标是用较少篇幅把 Tour Pass 的业务目标、技术结构、核心算法、接口链路和可讲亮点串起来。更细的接口字段见 `docs/api.md`，算法细节见 `docs/algorithm.md`，架构图见 `docs/architecture.md`。

## 1. 一句话介绍

Tour Pass 是一个用 C++17 实现的城市自由行行程规划算法服务。它把景点、餐厅、酒店、夜间活动点建模为 POI 图，根据用户兴趣、必去点、出发结束时间、节奏和候选数量，生成多日旅行路线，并解释为什么这样排。

面试中可以这样说：

> 我做的是一个面向城市自由行的 C++ 算法服务。核心不是简单推荐景点，而是把景点选择、通勤成本、开放时间、餐饮窗口、必去点覆盖和多候选方案对比放在同一个规划流程里，最后通过 Web 页面和 JSON API 可视化展示。

## 2. 这个项目解决什么问题

自由行规划看起来像“推荐几个景点”，实际有很多约束：

- 用户想去的兴趣点不同，例如历史文化、美食、夜景。
- 景点有开放时间，餐厅有午餐和晚餐窗口。
- 不同 POI 之间通勤时间不同，路线顺序会影响可行性。
- 用户可能需要多个方案，例如少走路、紧凑多玩、雨天室内。
- 面试或演示时必须能解释结果，而不是只给一个黑盒分数。

Tour Pass 的解法是把城市 POI 抽象成图，把通勤时间作为边权，把开放时间、停留时长、兴趣标签、热度、价格等作为节点属性，然后用图搜索、Beam Search、评分拆解和 Pareto 多目标排序生成可解释行程。

## 3. 技术栈与模块

- 后端语言：C++17
- HTTP 服务：`cpp-httplib`
- JSON：`nlohmann/json`
- 构建：Makefile + MinGW，也支持 CMake
- 数据：本地 `data/pois.json` 和 `data/edges.json`
- 前端：`web/` 静态演示台，由 C++ 服务直接托管
- LLM：OpenAI/DeepSeek 兼容接口；无密钥或禁用时用本地中文模板兜底
- 质量保障：C++ 测试、数据校验脚本、API 冒烟脚本、UI 验证脚本、性能基准脚本、GitHub Actions

主要目录：

- `include/tourpass/`：模块接口和数据结构。
- `src/`：算法、服务端、数据加载、检索、LLM 实现。
- `data/`：长沙 POI 与通勤边样例数据。
- `web/`：本地可视化演示页面。
- `docs/`：API、架构、算法、简历表达、性能和面试材料。
- `tests/`：核心行为测试。
- `scripts/`：数据校验、演示、API 冒烟、UI 验证、性能基准。

## 4. 数据模型怎么理解

项目里有两类核心数据。

第一类是 POI 节点，来自 `data/pois.json`。一个 POI 代表酒店、景点、餐厅、夜间活动或交通点，包含：

- `id` / `name`：唯一标识和展示名称。
- `type`：类型，例如 attraction、restaurant、hotel、nightlife。
- `lat` / `lng`：位置坐标，用于 A* 启发式估计。
- `tags`：兴趣标签，例如历史文化、美食、室内、户外。
- `open_time` / `close_time`：开放时间。
- `visit_duration_minutes`：建议停留时长。
- `popularity` / `price_level`：热度与价格因素。
- `area` / `description`：区域和文本描述，用于展示与搜索。

第二类是通勤边，来自 `data/edges.json`。边连接两个 POI，包含步行、公交、打车等耗时。当前默认权重优先级是：

```text
transit_minutes -> taxi_minutes -> walk_minutes
```

也就是说，规划默认更偏公共交通场景；如果没有公交耗时，就退到打车或步行耗时。

## 5. 一次请求的核心流程

以 `/trip/plan` 为例：

1. 服务启动时加载 POI 和边数据。
2. `PoiGraph` 建立 id/name 索引和邻接表。
3. API 解析用户偏好为 `TripRequest`。
4. `TripPlanner` 选择酒店作为每天起点。
5. 每天按固定时间槽规划：上午、午餐、下午、晚餐、晚上。
6. 每个时间槽筛选候选 POI，并用评分函数计算兴趣、热度、必去、通勤、价格、时间窗等因素。
7. Beam Search 保留 Top-K 个局部状态，避免贪心只走一个早期选择。
8. 生成每日行程后做时间窗复核，包括开放时间、餐饮窗口、站点顺序和当日结束时间。
9. 对候选方案计算 KPI、Pareto 层级和多样性指标。
10. 返回结构化 JSON，Web 页面再把候选对比、路线、时间轴、算法解释和工具箱展示出来。

## 6. 核心算法怎么讲

### 6.1 Dijkstra 与 A*

`PoiGraph` 提供两种最短路查询：

- Dijkstra：在非负边权图上保证最短通勤时间。
- A*：在 Dijkstra 基础上加入经纬度直线距离启发式，用于展示启发式图搜索能力。

复杂度可以讲：

```text
Dijkstra: O((V + E) log V)
A*: 最坏仍是 O((V + E) log V)，启发式有效时实际扩展节点更少
```

在当前样例数据较小的情况下，二者都很快；保留 A* 主要是为了展示工程扩展性和算法完整性。

### 6.2 Beam Search 行程规划

项目没有用纯贪心，因为贪心每个时间槽只选当前最高分 POI，容易导致后续餐饮窗口、闭馆时间或通勤顺序变差。

Beam Search 的做法是：

- 每个状态记录已选站点、已用 POI、当前位置、当前时间、累计通勤、累计游玩和累计得分。
- 每个时间槽展开多个候选 POI。
- 按 `interest_score - travel_penalty + stop_count bonus` 排序。
- 每轮只保留最多 Top-K 个状态。

这样可以在速度、可解释性和路线质量之间做平衡。它不承诺全局最优，但比单路径贪心更稳，也比完整枚举更适合面试演示和小型服务。

### 6.3 评分拆解

每个站点会输出 `score_breakdown`，主要包括：

- 热度分
- 兴趣匹配
- 必去加权
- 策略加权
- 通勤惩罚
- 价格惩罚
- 等待或闭馆惩罚

这让项目能回答“为什么选这个点”，也能让候选方案差异不是只改名字，而是由真实权重影响 POI 选择。

### 6.4 多候选与 Pareto 排序

当 `candidate_count > 1` 时，系统会生成多个策略候选：

- 轻松少走路
- 紧凑多覆盖
- 文化优先
- 美食优先
- 雨天室内

每个候选都计算指标，例如总评分、总站点数、总通勤、必去覆盖、开放时间风险、未安排数量。然后用 Pareto 非支配分层解释多目标取舍：

> 如果方案 A 在所有目标上都不差于方案 B，并且至少一个目标更好，那么 A 支配 B。没有被其他候选支配的方案处于第 1 层。

这个设计能避免把所有因素粗暴压成一个黑盒总分，更适合解释“高评分、低通勤、低风险、必去覆盖”之间的取舍。

### 6.5 BM25 检索

`/poi/search` 使用轻量 BM25 思路检索 POI 文本，字段权重包括：

- 名称：权重最高
- 标签：次高
- 区域：中等
- 描述：基础权重

最终还叠加 POI 热度，并返回 `matched_terms`、`score_explanation` 和 `score_contributions`，便于解释检索结果为什么排在前面。

## 7. API 怎么讲

核心接口：

- `GET /health`：健康检查，返回数据与 LLM 状态。
- `POST /trip/plan`：生成单个或多个候选行程。
- `GET /route/shortest`：查询两个 POI 之间的 Dijkstra 或 A* 最短路。
- `GET /poi/search`：按关键词检索 POI。
- `POST /trip/alternatives`：根据下雨、闭馆、太累、预算降低等场景返回替换点。
- `POST /itinerary/explain`：生成行程中文解释，优先远程 LLM，失败时模板兜底。

错误统一返回：

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "请求参数不合法",
    "details": {}
  }
}
```

这个点可以用来说明 API 不是随手拼的，而是考虑了调用方处理错误的稳定格式。

## 8. 工程质量怎么讲

项目不只写算法，还补了工程闭环：

- `tests/test_main.cpp` 覆盖数据加载、最短路、规划、候选方案、评分拆解、Pareto、多样性、BM25、LLM 兜底等核心行为。
- `scripts/validate_data.js` 校验 POI 字段、坐标、时间窗、类型覆盖、边引用、边权合法性和图连通性。
- `scripts/api_smoke.ps1` 可启动服务并验证核心 API。
- `scripts/benchmark.js` 输出接口 avg/p50/p95 性能基准。
- `.github/workflows/ci.yml` 做跨平台 CMake/CTest 和 Windows API 冒烟验证。

面试中可以强调：这个项目的质量门禁覆盖了“代码能跑、数据可信、接口可用、性能不明显回退”四件事。

## 9. LLM 在项目里的位置

LLM 不是核心规划算法，而是解释层增强。核心行程由 C++ 结构化算法生成；LLM 只负责把结构化行程转换成更自然的中文说明。

这样设计有两个好处：

- 没有 API Key 或网络失败时，项目仍然可以通过模板稳定演示。
- 规划结果可控、可测试，不依赖 LLM 随机输出决定路线。

面试时可以说：

> 我把 LLM 放在解释层，而不是决策层。路线生成仍由可测试的 C++ 算法完成，这样离线可演示，也更容易排查和验证。

## 10. 项目亮点总结

- 把旅游规划抽象成带时间窗的 POI 图。
- 使用 Dijkstra/A* 解决点到点通勤问题。
- 使用 Beam Search 做日内时间槽调度，避免纯贪心。
- 用评分拆解解释每个 POI 的选择依据。
- 用多策略生成候选方案，而不是只给一个固定路线。
- 用 Pareto 非支配排序解释多目标取舍。
- 用 BM25 + 字段权重做 POI 检索并返回排序贡献。
- 用 LLM/模板生成自然语言解释，但核心算法不依赖 LLM。
- 提供 Web 演示台、API 文档、性能基准、CI 和数据质量门禁。

## 11. 当前边界与可优化方向

当前项目是面向面试展示的 MVP，有明确边界：

- 数据是长沙样例数据，不接真实地图、天气、拥堵或闭馆 API。
- 通勤边来自人工样例，不代表实时路况。
- Beam Search 不保证全局最优，但在当前规模和可解释目标下更合适。
- 中文检索主要依赖空格切分和子串匹配，后续可接中文分词、拼音召回或向量检索。
- 评分权重是规则设计，后续可根据用户点击、收藏、停留、跳过等行为学习权重。
- 后续可接真实地图服务、天气服务、数据库、多城市数据和用户系统。

面试收尾可以这样讲：

> 这个项目目前更像一个可解释的行程规划算法原型。它的重点是把图搜索、时间窗调度、多目标候选对比和工程化 API 跑通。后续如果产品化，我会优先补真实地图数据、多城市数据、用户画像和在线反馈学习。
