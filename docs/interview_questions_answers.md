# Tour Pass 面试高频问题与标准答案

这份文档用于准备面试问答。回答尽量采用“先结论，再技术细节，再取舍”的方式，避免只背名词。

## 1. 你这个项目是做什么的？

标准答案：

Tour Pass 是一个 C++17 城市自由行行程规划算法服务。它把酒店、景点、餐厅和夜间活动点抽象成 POI 图，用通勤时间作为边权，用开放时间、停留时长、兴趣标签、热度和价格作为节点属性。用户输入城市、天数、兴趣、必去点、节奏和候选数量后，系统会生成多日行程，并返回候选方案对比、站点评分拆解、时间窗复核、最短路查询和自然语言解释。

可以补一句亮点：

项目重点不是简单推荐景点，而是把“去哪、怎么排、时间是否可行、为什么这么排、有没有替代方案”放在同一个可解释规划流程里。

## 2. 为什么选择 C++17？

标准答案：

这个项目的核心是图搜索、路线评分和候选状态扩展，C++ 比较适合表达底层数据结构和算法过程，也方便展示我对算法复杂度、内存结构和工程构建的掌握。项目使用 C++17 是因为它提供了足够现代的标准库能力，例如 `vector`、`unordered_map`、`priority_queue`、结构体建模和异常处理，同时不会引入太重的运行时依赖。

取舍：

如果项目要快速做商业后台，Java、Go 或 Python 会更快；但作为面试项目，C++17 更能体现算法实现、服务封装和工程化能力。

## 3. 整体架构是什么？

标准答案：

整体分为五层：

1. 数据层：`data/pois.json` 和 `data/edges.json` 保存 POI 和通勤边。
2. 图层：`PoiGraph` 建索引和邻接表，提供 Dijkstra/A* 最短路。
3. 规划层：`TripPlanner` 根据用户偏好做 Beam Search、评分、时间窗复核和候选方案生成。
4. 能力层：`SearchEngine` 做 BM25 检索，`LlmClient` 做 LLM/模板解释。
5. API 与展示层：`cpp-httplib` 提供 HTTP JSON API，`web/` 做本地演示台。

这样拆分的好处是路线计算、行程规划、搜索解释、LLM 解释和 HTTP 服务之间职责清晰，后续替换数据源或接真实地图 API 时影响范围较小。

## 4. POI 图是怎么建模的？

标准答案：

POI 是图节点，包括 id、名称、类型、经纬度、标签、开放时间、停留时长、热度、价格、区域和描述。边表示两个 POI 之间的通勤关系，包括距离、步行、公交、打车耗时。当前图按无向图处理，默认通勤权重优先使用 `transit_minutes`，没有公交耗时再退到打车或步行耗时。

这样做的原因是自由行规划不只是空间距离问题，还受时间窗、游玩时长和用户兴趣影响，所以节点要带业务属性，边要带通勤成本。

## 5. 为什么用 Dijkstra？

标准答案：

POI 图上的通勤时间是非负边权，Dijkstra 正好适合求单源到目标的最短路径，可以保证得到最短通勤时间。项目里最短路结果一方面用于 `/route/shortest` 接口，另一方面会进入站点评分函数，作为通勤惩罚影响行程顺序。

复杂度是：

```text
O((V + E) log V)
```

项目用 `priority_queue` 实现，适合当前样例规模，也方便后续扩展到更多 POI。

## 6. A* 和 Dijkstra 的区别是什么？项目里为什么保留 A*？

标准答案：

Dijkstra 只按当前已知最短距离扩展；A* 在此基础上加入启发函数 `f(n)=g(n)+h(n)`，其中 `g(n)` 是起点到当前点的已知成本，`h(n)` 是当前点到目标的估计成本。项目里的 `h(n)` 用经纬度粗略估算直线距离，再按城市通勤速度换算成分钟。

保留 A* 的原因是：当前数据很小，性能差异不明显，但 A* 展示了在更大 POI 图上减少搜索空间的思路，也让 `/route/shortest` 可以对比两类常见图搜索算法。

## 7. 行程规划为什么不用纯贪心？

标准答案：

纯贪心每个时间槽只选当前分数最高的 POI，很容易过早锁定局部最优。例如上午选了一个高分但很远的景点，可能导致午餐窗口赶不上，下午闭馆，或者晚上通勤变长。旅游规划有强顺序依赖，当前选择会影响后续时间窗和通勤成本。

所以项目用 Beam Search。它在每个时间槽保留多个 Top-K 局部状态，既避免完整枚举的组合爆炸，又比单路径贪心更稳。

## 8. Beam Search 在项目里具体怎么做？

标准答案：

一天被拆成上午、午餐、下午、晚餐、晚上几个时间槽。每个 Beam 状态保存已选站点、已用 POI、当前位置、当前时间、累计通勤、累计游玩和累计兴趣得分。

每处理一个时间槽，系统会：

1. 根据时间槽筛选 POI 类型，例如午餐和晚餐只选餐厅。
2. 对候选 POI 计算评分。
3. 展开当前 Beam 状态形成下一批状态。
4. 按状态分数排序。
5. 保留 Top-K 个状态继续向后扩展。

状态分数大致是：

```text
interest_score - total_travel_minutes * travel_penalty + stop_count_bonus
```

这样能在兴趣匹配、通勤成本和覆盖数量之间平衡。

## 9. Beam Search 能保证全局最优吗？

标准答案：

不能。Beam Search 是启发式搜索，它通过限制 beam width 控制搜索规模，因此不保证全局最优。但对这个项目来说，目标不是求旅行商问题式的全局最优，而是在小规模样例数据上快速生成可解释、可对比、时间窗可行的候选路线。

它的优势是：

- 比纯贪心更不容易陷入早期局部选择。
- 比完整枚举更快，适合 API 服务。
- Beam trace 可以输出调试过程，便于面试解释。

## 10. 评分函数包括哪些因素？

标准答案：

站点评分会拆成多个组件：

- 热度：热门 POI 基础分更高。
- 兴趣匹配：命中用户兴趣标签会加分。
- 必去加权：用户 must_visit 命中时大幅加分。
- 策略加权：例如文化优先、美食优先、雨天室内。
- 通勤惩罚：从上一站过来越远扣分越多。
- 价格惩罚：消费等级越高扣分越多。
- 时间窗惩罚：早到等待或超过关闭时间会扣分。

响应里会输出 `score_breakdown`，所以可以解释每个站点为什么被选中。

## 11. 多候选方案是怎么生成的？

标准答案：

当 `candidate_count > 1` 时，系统会生成多个不同策略的 TripRequest 变体，例如：

- 轻松少走路：提高通勤惩罚，偏好同区域和短通勤。
- 紧凑多覆盖：降低通勤惩罚，提高覆盖数量和高热度权重。
- 文化优先：加权博物馆、书院、古建筑等标签。
- 美食优先：加权餐饮、小吃、夜市和茶饮相关标签。
- 雨天室内：加权室内 POI，降低户外点优先级。

这些不是只改方案名称，而是进入评分函数影响真实 POI 选择和路线结果。

## 12. Pareto 非支配排序在项目中有什么作用？

标准答案：

候选路线不是只有一个目标。高评分、低通勤、少风险、必去覆盖多之间经常互相冲突。如果强行压成一个总分，面试官很难看出方案之间的取舍。

所以项目用 Pareto 非支配分层：如果方案 A 在所有目标上都不差于方案 B，并且至少一个目标更好，那么 A 支配 B。没有被其他方案支配的候选进入 Pareto 第 1 层。

项目会输出 `pareto_rank`、`dominated`、`tradeoff_summary` 和 `pareto_debug`，用于解释某个候选为什么是第一层，或者为什么存在取舍成本。

## 13. 候选多样性怎么衡量？

标准答案：

项目把第一个候选作为基线，对其他候选计算：

- POI 重合率
- 区域重合率
- 独有 POI 数量
- 独有 POI 名称
- 多样性标签和摘要

重合率使用类似 Jaccard overlap 的集合计算。这样可以说明多个候选是不是“真的不同”，而不是同一条路线换个标题。

## 14. 时间窗约束怎么处理？

标准答案：

项目有两层时间窗处理。

第一层是在 Beam Search 扩展候选时过滤明显不可行的安排，例如餐厅必须完整落在午餐 `11:30-13:30` 或晚餐 `17:30-19:30` 窗口内。

第二层是在生成每日路线后做统一复核，检查：

- 站点顺序是否前后冲突。
- 是否早于开放时间，需要等待。
- 是否超过关闭时间。
- 餐饮是否完整落在餐饮窗口。
- 是否超过当天结束时间。

响应会输出 `time_window_status`、`time_window_reason`、`time_window_feasible` 和 `time_window_diagnostics`。

## 15. 为什么要做日内局部交换优化？

标准答案：

Beam Search 先按时间槽语义生成路线，例如上午、午餐、下午、晚餐、晚上。生成后，项目会对非餐饮站点做局部交换，评估理论上能否减少通勤。

但是项目不会盲目重排时间线。只有交换后仍满足开放时间、餐饮窗口和站点顺序约束时，才计入优化收益。这样可以说明算法知道更短通勤的可能性，同时尊重用户对一天节奏的理解。

## 16. BM25 检索是怎么实现的？

标准答案：

`/poi/search` 使用轻量 BM25 思路。查询词会和 POI 的名称、标签、区域、描述进行匹配，不同字段有不同权重：

- 名称权重最高。
- 标签次高。
- 区域和描述权重相对低。

系统计算词频饱和项和 IDF，再叠加 POI 热度，最后按分数排序。响应里会返回匹配词、排序解释和字段贡献，用于说明为什么某个 POI 排在前面。

## 17. 中文检索有什么局限？

标准答案：

当前中文检索主要依赖空格切分和子串匹配，适合演示和可控样例数据，但不等同于完整中文搜索引擎。后续可以接中文分词、拼音召回、同义词词典，或者向量检索来提升召回能力。

这也是项目当前 MVP 的明确边界。

## 18. LLM 在项目中负责什么？

标准答案：

LLM 只负责解释层，不负责核心决策。路线生成、候选排序、时间窗复核和评分拆解都由 C++ 结构化算法完成。`/itinerary/explain` 会把行程转成自然语言说明；如果没有 API Key、设置了 `LLM_DISABLED=1`，或者远程调用失败，就回退到本地中文模板。

这样设计的好处是结果稳定、可测试、可离线演示，同时还能用 LLM 提升表达体验。

## 19. 为什么不让 LLM 直接规划路线？

标准答案：

因为行程规划涉及明确的约束和可验证结果，例如开放时间、餐饮窗口、通勤时间、必去覆盖。让 LLM 直接规划容易出现幻觉，结果也不稳定，难以做单元测试。

我把 LLM 放在解释层，核心规划由确定性算法完成，这样既能保证可控性，也能保留自然语言解释的优势。

## 20. 项目有哪些 API？

标准答案：

主要有六个：

- `GET /health`：健康检查。
- `POST /trip/plan`：生成行程或候选行程。
- `GET /route/shortest`：查询 Dijkstra/A* 最短路径。
- `GET /poi/search`：检索 POI。
- `POST /trip/alternatives`：根据下雨、闭馆、太累、预算降低等场景给替换方案。
- `POST /itinerary/explain`：生成行程解释。

所有错误统一返回 `{ "error": { "code", "message", "details" } }`，方便前端或调用方稳定处理。

## 21. 项目怎么保证数据质量？

标准答案：

项目提供两层数据入口。`scripts/import_real_pois.js` 可以把 CSV/JSON 形式的真实 POI 清单标准化成项目的 `pois.json`，并按地理距离生成近邻通勤边；`scripts/validate_data.js` 做数据质量门禁，既能校验默认 `data/`，也能通过 `--pois` / `--edges` 校验导入后的临时数据集。

数据质量门禁检查：

- POI 必填字段和类型是否合法。
- 坐标、时间窗、热度、价格范围是否合法。
- POI id 是否重复。
- 标签是否为空或重复。
- 是否至少覆盖酒店、景点、餐厅、夜间活动等必要类型。
- 边是否引用存在的 POI。
- 边权是否合法。
- 无向图是否连通。

这很重要，因为路线算法的质量不仅取决于代码，也取决于输入数据是否可信。

## 22. 项目怎么测试？

标准答案：

测试主要覆盖几个方向：

- 数据加载和图构建。
- Dijkstra/A* 最短路正确性。
- 多日规划是否生成站点、午餐、晚餐和必去点。
- 严格时间窗诊断。
- 未安排必去点原因。
- 多候选策略是否真的应用权重。
- Pareto 分层和候选多样性指标。
- Beam Search 调试轨迹。
- BM25 检索和排序解释。
- LLM 模板兜底、禁用开关和内置 HTTP client。

项目也有 CI、API 冒烟、UI 验证和性能基准，覆盖从单元行为到服务可用性。

## 23. 性能情况怎么样？

标准答案：

当前默认数据集是演示规模：长沙样例图有 `25` 个 POI 节点、`46` 条通勤边。性能数据只能说明本地样例、synthetic 规模趋势和回归检查，不能包装成生产压测。

为了回答“POI 扩大后怎么办”，项目做了三类热路径优化：第一，启动期预计算 POI 两两最短通勤缓存，让规划阶段重复通勤查询变成 O(1)；第二，Beam Search 前先按类型、时间窗、策略标签和必去点做候选召回裁剪，不让全量 POI 直接进入状态扩展；第三，候选排序阶段复用评分和通勤结果，避免 comparator 里重复评分。

当前 synthetic 规模实验使用 `LLM_DISABLED=1`，覆盖 25/100/500 POI，并记录 avg/p95/max、失败数和最短路缓存 entries。这个数字只能说明本地算法热路径趋势，不包含真实地图 API、真实交通、真实用户流量或外部 LLM 延迟。

缓存命中率只用于验证 LRU/TTL 缓存链路是否生效，不代表真实线上流量命中率。讲性能时要区分热缓存、冷缓存和强制绕过缓存的真实规划耗时。

可以补充：

后续数据规模继续扩大后，不能无脑全量预计算所有 POI 两两最短路，因为它是 O(POI^2) 空间。几万 POI 时应改成热点最短路缓存、区域分层图、按需缓存、检索倒排索引和候选方案并行生成。

## 24. 如果 POI 数量扩大到几万，怎么优化？

标准答案：

可以分层优化：

- 图搜索层：小到中等规模可以预计算 POI 两两最短路；更大规模改为热点缓存、按需缓存或区域分层图。
- 候选召回层：先按城市区域、类型、标签、开放时间和必去点过滤，再进入 Beam Search。
- 检索层：把当前实时扫描改为倒排索引或搜索引擎。
- 规划层：缓存评分组件，限制候选池和 branch factor，引入区域聚类。
- 系统层：候选方案并行计算，接口结果缓存，数据加载改为数据库或内存索引。

核心思路是不能让 Beam Search 直接面对全量 POI，而要先召回小而高质量的候选集。

## 25. 如果接真实地图 API，你会怎么改？

标准答案：

我会把当前 `edges.json` 的通勤边抽象成一个 `TravelTimeProvider`，支持本地样例数据和真实地图 API 两种实现。规划器只依赖“从 A 到 B 的通勤时间”接口，不关心数据来自本地 JSON 还是地图服务。

同时会加缓存，因为通勤查询成本高且容易重复。对于真实地图返回失败的情况，也要保留本地估算或上一次缓存结果，避免整个规划接口不可用。

## 26. 如果接数据库，你会怎么设计？

标准答案：

当前已经接入 SQLite，但定位是持久化规划请求历史、异步任务结果、benchmark 运行记录和数据版本，不是把数据库放进规划热路径。POI 和边仍在服务启动时加载到内存图，避免每次算法计算都查库。这样讲更可信：数据库证明持久化和实验记录能力，并发证明单机背压和可观测能力，但不说“数据库支撑高并发”。

需要注意数据版本。行程结果最好记录使用的数据版本，避免用户复查时发现 POI 或通勤数据已经变化。

## 27. 这个项目最难的点是什么？

标准答案：

最难的不是单个算法，而是把多个约束放进一个可解释流程里。旅游规划同时受兴趣、通勤、开放时间、餐饮窗口、必去点、节奏和候选多样性影响。单纯最短路或单纯推荐都不够。

我做的重点是把图搜索提供的通勤成本、Beam Search 的时间槽状态、评分拆解、时间窗复核和 Pareto 多目标排序串起来，并在 API 和 Web 页面上解释清楚。

## 28. 这个项目和普通 CRUD 项目相比亮点在哪里？

标准答案：

它不是简单增删改查，而是一个算法服务。核心亮点包括：

- 图建模和最短路。
- Beam Search 时间窗调度。
- 多策略候选生成。
- Pareto 多目标取舍。
- BM25 检索解释。
- LLM/模板解释兜底。
- 数据校验、CI、性能基准和 Web 演示闭环。

它能体现算法、后端 API、工程质量和产品展示能力。

## 29. 项目有哪些不足？

标准答案：

当前不足主要是 MVP 边界：

- POI 和边是人工样例数据，不代表实时路况和营业状态。
- 没接真实地图、天气、排队、闭馆 API。
- Beam Search 是启发式算法，不保证全局最优。
- 中文检索还不是完整中文搜索系统。
- 评分权重是规则设计，还没有用户行为数据训练。
- 当前没有真实用户系统和持久化行程历史。

但这些边界是有意识控制的，目的是优先把核心规划链路、可解释性和离线演示跑通。

## 32. 项目中怎么体现可解释性？

标准答案：

可解释性体现在四层：

- 站点层：每个 stop 有 reason 和 score_breakdown。
- 天级层：每天有 summary、optimization_summary、constraint_explanations、time_window_diagnostics。
- 候选层：每个候选有 comparison、pareto_rank、tradeoff_summary、diversity_summary。
- 检索层：搜索结果有 matched_terms、score_explanation、score_contributions。

所以用户不仅看到结果，还能看到算法为什么这样选择。

## 33. 如果面试官问“这个项目 AI 在哪里”，怎么答？

标准答案：

这个项目的 AI 可以分两层讲。

第一层是传统算法智能：图搜索、Beam Search、多目标排序、检索排序和规则评分，这些是核心决策逻辑。

第二层是大模型解释：LLM 负责把结构化路线转成自然语言说明，但不直接决定路线。这样既能结合大模型能力，又避免把核心约束交给不可控输出。

## 35. 简历上这项目应该怎么概括？

标准答案：

可以写：

> 基于 C++17 实现城市自由行结构化行程规划算法服务，将 POI、通勤边、开放时间、停留时长和兴趣标签建模为带时间窗约束的图；结合两两最短路缓存、候选召回裁剪、Beam Search Top-K 调度、评分拆解、Pareto 多目标排序、BM25 检索和 LLM/模板解释生成可解释多日候选行程；补充 synthetic 25/100/500 POI 规模实验、性能回归 benchmark、数据校验、CI 和本地 Web 演示台，用于验证规划链路稳定性与规模瓶颈。

## 36. 面试追问：为什么不用动态规划？

标准答案：

如果把 POI 子集、当前点、时间都纳入状态，动态规划会接近带时间窗的 Orienteering/TSP 变体，状态空间很大，且还要处理餐饮槽、必去点、用户兴趣和多候选策略。对当前项目来说，完整 DP 的复杂度和实现成本偏高。

Beam Search 更适合当前目标：它能保留多个局部状态，控制复杂度，并输出可解释的搜索轨迹。后续如果数据规模和目标更明确，可以针对部分子问题引入 DP 或更严格的优化算法。

## 37. 面试追问：为什么不用遗传算法或蚁群算法？

标准答案：

遗传算法和蚁群算法适合复杂组合优化，但结果解释成本较高，参数调优也更复杂。这个项目面向面试展示，需要稳定、可复现、可解释，并且要把餐饮窗口和开放时间讲清楚。

Beam Search 更直接，状态、扩展、保留和评分都能在响应里输出，便于调试和讲解。

## 38. 面试追问：如何避免候选方案同质化？

标准答案：

项目从两个层面处理。

第一，生成阶段使用不同策略权重，例如低通勤、紧凑、文化、美食、雨天室内，直接影响 POI 选择。

第二，结果阶段计算 POI 重合率、区域重合率、独有 POI 和多样性标签，量化候选之间是否真的不同。

如果继续优化，还可以在生成阶段加入 diversity penalty，对已经出现在基线方案里的 POI 降权。

## 39. 面试追问：如果用户必去点排不进去怎么办？

标准答案：

系统会优先给必去点加权，但如果受开放时间、通勤、当天结束时间或数据缺失限制，仍可能无法安排。项目会在 `unscheduled_reasons` 中明确输出原因，例如样例数据不存在该 POI，或者时间预算不足。

这比强行塞进不可行路线更合理，因为旅游规划要保证结果可信。

## 40. 面试追问：如何处理服务稳定性？

标准答案：

当前服务稳定性主要靠几件事：

- 启动时加载本地数据，避免核心请求依赖外部服务。
- LLM 失败自动模板兜底。
- 参数错误统一返回 JSON 错误。
- 数据质量脚本阻止坏数据进入。
- 测试覆盖核心算法行为。
- CI 覆盖构建、CTest 和 API 冒烟。
- 性能基准用于发现明显回退。

后续生产化会增加日志、监控、超时控制、请求限流和真实缓存。

## 41. 面试追问：这个项目是不是过度包装了？

标准答案：

我会把它定位为 C++ 算法服务作品集，而不是已经上线的商业旅游平台。项目确实包含图搜索、Beam Search、BM25、候选策略、缓存、异步任务和指标接口，但它们都是围绕一个小规模长沙样例数据集做的可演示闭环。

我在简历和面试里会明确三个边界：

## 42. 面试追问：这么短时间怎么完成这么多模块？

标准答案：

这个项目不是从零做一个商业系统，而是围绕“城市行程规划”这个单一主题做迭代式作品集。实现顺序是从最小闭环开始：先做 POI/边数据和 Dijkstra，再做 `/trip/plan`，然后补多候选策略、解释字段、Web 演示、测试、CI、benchmark，最后补缓存、异步任务和指标。

## 43. 面试追问：为什么用 cpp-httplib，不用 Drogon 这类框架？

标准答案：

因为这个项目的重点是算法链路和可解释规划，不是 C++ Web 框架本身。`cpp-httplib` 是单头文件，依赖少，方便在 Windows 本地快速构建和演示，也足够承载 JSON API、静态页面、请求头、中间件 hook 和轻量线程池配置。

但我不会把它包装成生产最佳实践。如果要生产化，我会评估 Drogon、Pistache、Boost.Beast，或者把算法服务封成库，由 Go/Java 后端托管业务 API。生产场景还需要更完整的连接治理、监控、限流、日志和部署方案。

## 44. 面试追问：哪些是自己实现，哪些是第三方？

标准答案：

自己实现的部分包括 POI/边数据模型、图索引、Dijkstra/A* 调用封装、Beam Search 日内调度、候选策略权重、评分拆解、时间窗复核、Pareto 分层、BM25 字段权重检索、LRU/TTL 缓存、异步任务仓库、指标 JSON 和 Web 演示页面联调。

第三方主要是 `cpp-httplib`、`nlohmann/json` 和可选的 OpenAI/DeepSeek 兼容 LLM 接口。LLM 只做解释层，路线决策由 C++ 结构化算法完成。

## 45. LLM 在你的系统中扮演什么角色？为什么不直接用 LLM 生成行程？

标准答案：

LLM 在系统中有两个角色：意图解析和文案生成。`POST /trip/chat` 端点接收用户的自然语言输入，LLM 负责从中提取结构化参数（天数、兴趣、必去景点、节奏等），然后调用 Beam Search 引擎生成行程，最后 LLM 再将结构化行程转化为自然语言回复。

不直接用 LLM 生成行程的原因有三个：
1. **可控性**：Beam Search 保证时间窗约束、开放时间、餐饮窗口等硬约束被满足，LLM 生成的行程无法保证这些约束。
2. **可解释性**：每个站点的选择都有评分拆解、Beam Search 轨迹和 Pareto 排名，可以追溯决策过程。
3. **一致性**：相同输入总是产生相同结果（在确定性算法下），LLM 有随机性。

这是 Hybrid AI 架构的思路：LLM 擅长理解和生成自然语言，传统算法擅长约束求解，各取所长。

## 46. TravelTimeProvider 是什么设计模式？为什么这样设计？

标准答案：

TravelTimeProvider 是 Strategy Pattern。它定义了一个通勤时间查询的抽象接口，有两个具体实现：`LocalDataProvider`（读取本地 edges.json 的最短路径缓存）和 `AmapLiveProvider`（调用高德实时路线 API，带 LRU 缓存和 API 失败时自动 fallback 到本地数据）。

这样设计的原因：
1. **解耦**：规划算法不依赖具体的通勤数据来源，通过 `TOURPASS_TRAVEL_TIME_PROVIDER=local|amap` 环境变量切换。
2. **可测试**：可以用 mock provider 测试规划逻辑，不依赖外部 API。
3. **渐进迁移**：可以先用本地数据开发和演示，部署时切到实时 API，不需要改任何代码。
4. **容错**：AmapLiveProvider 在 API 调用失败时自动回退到本地数据，保证服务可用性。

## 47. 你是怎么处理 LLM 输出的 POI 名称与数据库不完全匹配的问题？

标准答案：

用户说"岳麓山"，但 POI 数据库里的全名可能是"岳麓山风景名胜区"。系统用 BM25 搜索引擎做模糊匹配：对 LLM 提取的每个必去景点名称，调用 SearchEngine 的 search 方法，取 BM25 分数最高的结果。分数 > 5.0 判定为高置信匹配，2.0-5.0 为中等置信，< 2.0 则认为未找到并提示用户。

这个方案复用了已有的 BM25 检索模块，不需要额外引入编辑距离或拼音匹配库。BM25 本身对部分匹配和词频有天然的容错能力。

## 48. 如果要支持实时交通数据，你的系统架构需要怎么调整？

标准答案：

已经支持了。TravelTimeProvider 抽象层允许通过环境变量切换数据源：
- `TOURPASS_TRAVEL_TIME_PROVIDER=local`：使用启动时加载的 edges.json 数据。
- `TOURPASS_TRAVEL_TIME_PROVIDER=amap`：调用高德实时路线 API，带 LRU 缓存（10000 条目，1 小时 TTL），API 失败时自动回退到本地数据。

AmapLiveProvider 的缓存策略是：相同 POI 对的结果缓存 1 小时，避免重复调用 API。缓存使用 LRU 淘汰策略，容量可通过环境变量配置。

## 49. 多城市支持是怎么实现的？

标准答案：

通过 `TOURPASS_CITY` 环境变量选择加载哪个城市的数据。数据目录结构为 `data/{city}/pois.json` 和 `data/{city}/edges.json`，启动时根据城市名拼接路径。已有的 `TOURPASS_POIS_PATH` / `TOURPASS_EDGES_PATH` 环境变量仍然可以覆盖默认路径。

这个设计的好处是：添加新城市只需要采集 POI 和通勤边数据，不需要改任何 C++ 代码。已提供 `config/amap.wuhan.json` 作为武汉的采集配置模板，可以复用已有的高德 POI 采集和通勤边生成 pipeline。
