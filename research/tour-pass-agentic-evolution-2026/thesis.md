# Thesis

## Central Thesis

Tour Pass 的上限并没有被“旅游规划可优化空间不足”封死；真正的瓶颈是系统把核心对象定义成一次性生成的行程文档。应把核心对象升级为可持续数天或数周、能保存事件、按需调用工具、遇到变化自动重规划、在副作用前请求批准、并从用户编辑中学习的 `Trip Mission`。C++ 约束规划器继续做确定性求解，Agent 负责决定何时查什么、何时追问、何时重算、何时执行以及何时升级给用户。

这个判断可证伪：如果在一组真实多轮任务上，持久会话、按需工具、事件驱动重规划和编辑反馈不能提高约束成功率、减少无效编辑或提高行程采纳率，那么升级为长期 Agent 没有足够收益，应保留当前工作流。

## Common Misreading

常见但不完整的理解是：“项目已经有 Intent、POI、Hotel、Weather、Restaurant、Scheduler、Reviewer、Ticket、Summary 多个 Agent，所以只需再增加交通、预算或领队 Agent。”

问题在于这些角色多数没有独立工具权限、状态所有权或动态决策边界。继续拆角色会增加 prompt、trace 和故障面，却不会改变产品仍然只交付一份静态路线的事实。

## Supportin  g Evidence

1. `graph.py::build_tour_graph` 是静态 StateGraph，模型不决定下一步用哪个数据源或工具；当前实现更接近可靠的 agentic workflow。
2. `MemorySaver`、每请求新 `thread_id`、30 分钟 SessionStore 和残留 `_chat_sessions` 构成了不一致的会话层，尚不能支持跨重启、跨天或审批暂停后的同一任务续跑。
3. 编辑器已记录用户删除、换序、跨天移动和改时间等强反馈，但这些行为没有进入长期偏好、检索样例或评估数据集。
4. 2025-2026 年官方 Agent 设计共同强调：状态与上下文分离、按需上下文、工具边界、可恢复执行、审批、trace 和 eval，而不是更多角色名。
5. TravelPlanner 说明真实旅游规划的困难正来自工具选择和多约束持续跟踪，这与 Tour Pass 的确定性 C++ 规划器互补，而不是要求用 LLM 替换它。

## Counterargument

旅行计划本身是一个边界清晰、约束强、适合确定性求解的任务。更自治的 Agent 会增加延迟、成本、不可预测性、安全审批和外部 API 故障，可能让作品集变得更复杂却更不可靠。当前“结构化输入 -> 规则/算法规划 -> 人工编辑”的产品也可能已经足够。

这个反论点成立于一次性、静态、无执行动作的行程生成。它不推翻长期旅行任务中的实时变化、跨服务动作和偏好学习价值。

## Conditions

判断成立的条件：

- 产品愿景覆盖行前准备和行中陪伴，而非只生成初稿。
- 至少接入两个有真实变化的工具面，例如实时天气/预警、营业/票务可用性、交通或日历。
- 会话事件和用户编辑可以持久化，并能建立可重复的真实任务评估。
- 所有写操作都具备幂等、权限、审批和审计边界。

判断失效的条件：

- 项目只用于展示 C++ 算法和一次性路线生成。
- 没有可靠外部数据或用户回访场景。
- Agent 指标不能优于现有规则工作流，或成本/延迟不可接受。

## Recommended Sequence

### P0 - 先补 Agent 运行时，而不是增加 Agent 数量

1. 统一 `TripSession`：以 append-only 事件记录输入、工具调用、规划版本、审批、编辑 diff 和执行结果；Graph checkpoint 只保存可恢复运行态，用户偏好单独进入长期 store。
2. 修复 SessionStore 迁移残留，并用同一 `trip_id/thread_id/user_id` 关联 API、LangGraph 和编辑器。
3. 为每次规划输出可追踪的 `plan_version`、数据时间、来源、工具调用、约束失败和降级警告。

### P1 - 建立一个真正的 Trip Orchestrator

保留 Scheduler/Reviewer 为有明确合同的能力工具，而不是继续命名更多 Agent。Orchestrator 可选择：

- `search_trip_evidence(city, query, freshness)`：按需检索攻略与事实；
- `check_route(from, to, depart_at)`：查询或验证路线；
- `check_place_status(poi, date)`：确认营业、闭馆、预约和可信度；
- `solve_itinerary(constraints, evidence_refs)`：调用现有 C++ 规划器；
- `validate_plan(plan_version)`：执行确定性约束和 Reviewer；
- `propose_patch(trigger, constraints)`：只生成差异而非整份覆盖；
- `apply_patch(...)`：需要用户批准时暂停并续跑。

让模型负责未知任务的查询和决策顺序，让算法负责可计算约束。这是 Tour Pass 最适合的 manager-as-tools 结构。

### P1 - 从“规划器”扩展为“旅行任务生命周期”

- 行前：缺失条件澄清、预约清单、预算检查、日历写入、价格/天气监控。
- 行中：天气预警、临时闭馆、交通延误、体力/时间偏差触发局部重规划。
- 行后：询问实际完成情况，把保留、删除、跳过、超时和评分写入偏好与评估。

### P1 - 先建 eval，再扩大自治

建立 50-200 个可复现任务，至少测：硬约束成功率、软偏好满足率、工具选择正确率、事实新鲜度、重规划 diff 大小、用户编辑距离、人工批准率、平均成本、p95 延迟和故障恢复。组件单测继续保留，但不作为 Agent 能力的替代指标。

### P2 - 谨慎引入的能力

- 长期偏好记忆：只存稳定、可编辑、带来源和时间的事实，如步行耐受、餐饮禁忌、酒店偏好；不要把完整聊天记录当记忆。
- 事件触发器：天气/闭馆/延误变化后自动形成重规划建议，不直接覆盖用户行程。
- 供应商工具适配层：可用 MCP 或内部统一协议做可替换接口，但先有第二个真实供应商再抽象。
- 多 Agent 并行研究：只用于跨城市、跨供应商或复杂证据搜集；常规 2-3 日城市游不需要。

### 暂时不要做

- 不要把每个领域对象都包装成自治 Agent。
- 不要为了“前沿”重写到另一个 Agent SDK；现有 LangGraph 足以实现持久状态、interrupt 和工具循环。
- 不要先上 A2A 或开放式多 Agent 社交协议；当前没有跨组织 Agent 互操作需求。
- 不要在没有幂等、审批和供应商授权前做自主预订或支付。
- 不要让 LLM 替代 C++ 约束求解器；TravelPlanner 的证据反而说明纯语言 Agent 容易漏约束。

## Unproven

- 用户是否真的需要行中 Agent，而不只是更好的初始路线。
- 哪种编辑 diff 最能预测用户长期偏好。
- 实时票务和营业数据能否以可接受的成本、许可和稳定性获得。
- 当前 DeepSeek 模型在工具选择、长时状态和结构化 patch 上的实际成功率。
- 引入 MCP 是否比现有 Python adapter 更省维护成本。
