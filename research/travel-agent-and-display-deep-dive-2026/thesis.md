# Thesis

## Central Thesis

对于只做旅游行程规划的 Tour Pass，最合适的 Agent 不是多角色 Crew，而是一个负责“取舍和解释”的行程规划 Agent，外加程序化的地点/路线/天气证据和确定性排程；前端则应从“Agent 工作台”切换为“可照着走的旅行手册”。

## Common Misreading

多 Agent 项目看起来更专业，但旅行规划的核心价值不是让多个角色互相对话，而是把用户约束转成少量可执行的行程节点，并让每个节点在时间、地点和证据上自洽。

## Supporting Evidence

1. Kbhujbal 的有效部分来自“解析—并行取数—编译”四步，而不是 3 个 agent 的人格；数据服务和 AI 的边界清楚（EV-001）。
2. Vikrambhat 的 LangGraph 主要节点仍是一次 Ollama 生成，附加 agent 由 UI 按需触发，说明更多节点并不等于更好的主行程（EV-002）。
3. Adrit 的 7 个 Agent 和 9 个顺序任务把研究、住宿、交通、天气、日程和预算串在一起，带来等待和长文本交接，但公开源码没有统一事实校验（EV-003）。
4. Skywain 把 plan JSON 设为唯一事实源，并用固定交付顺序、路线检查和主题渲染解决“结果可读性”，这比增加 Agent 更直接地改善用户体验（EV-007）。
5. Tour Pass 已有一次骨架调用、Provider 证据和 HardValidator，最短路径是重新组织显示层，而不是重写成 CrewAI/多 Agent 系统（EV-008）。

## Counterargument

单 Agent 可能在复杂多城市、预算权衡和文化解释上不够丰富；多 Agent 或研究子 Agent 能提供更多素材，且主题渲染会增加维护成本。若用户真的需要航班、住宿、签证、图片和预订链接，Kbhujbal 或 Skywain 的阶段模型会更完整。

## Conditions

这个判断适用于当前范围：城市内或少量城市的行程规划、用户有明确偏好、系统需要尽量快地交付一份能照着走的安排。若未来加入航班价格比较、酒店库存、签证和预订，再独立增加数据模块，不必预先把所有模块做成 Agent。

## Unproven

- 尚未用统一测试集证明单 Agent 与多 Agent 的最终行程质量差异。
- 尚未通过用户实验证明“旅行手册式页面”比当前页面有更高的完成率或信任度。
- 尚未验证参考图的精确视觉元素，因为该图片没有出现在当前工作区。
