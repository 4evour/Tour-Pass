# Thesis

## Central Thesis

这次返工先暴露了需求理解问题，Tour Pass 基准运行又证明需求会在系统内部被连续压缩。Codex 一开始没有识别用户要的是“可执行的人文旅行手册”；当完整需求被重新送进 Tour Pass 后，结构化模型无法表达分组返程，单次生成触顶后紧凑重试，自动修复继续删除执行节点，最后评分又把大量 unknown 判为通过。要解决的不是一条更长的提示词，而是从 Trip Brief 到事实、路线、内容、资产、出版和 QA 的生产对象与门禁。

## Common Misreading

一个容易接受但不完整的结论是：只要把模型提示词写得更文学，再把打印 CSS 调好，Tour Pass 就能生成同样的成品。

提示词确实能改善初稿，CSS 也能修复局部分页，但两者都解决不了来源有效期、影视剧情与现实地点的关系、图片授权、预约开窗、移动端跳转降级、多轮局部编辑和 PDF 逐页验收。缺少这些结构时，信息只能继续堆在 HTML 文本和人工记忆里。

## Supporting Evidence

1. `StructuredTripRequest` 已覆盖日期、城市、房型、预算、节奏、兴趣、预约偏好和每日时间窗，说明需求入口并不薄弱；但没有旅行项目、事实条目、图片资产或出版配置等实体。
2. 模型 Schema 只让模型输出路线骨架、每站短理由、酒店区域和少量说明，无法保存长篇景点资料、影视线索、官方规则版本或编辑批注。
3. `ItineraryAssembler` 能查询高德、天气与 12306，再确定性组装时间轴；其预约任务却把 `deadline` 和 `booking_url` 设为 `None`，证明“提醒用户核对”与“让用户直接执行”之间仍有产品缺口。
4. 本次成品必须另建 HTML、图片数组、打印 CSS 和 Playwright 导出脚本，并通过 contact sheet 反复看分页。它们没有进入 Tour Pass 的正式对象和测试链路。
5. Tour Pass 基准运行首次输出在 8,192 output tokens 截断，紧凑重试后又自动删除 6 个节点；最终实体绑定率只有 22.86%、开放核验为 0，仍通过 Hard Validator 并得到 84 分。
6. Tour Pass 自身基准 PDF 为 21 页，contact sheet 显示多页大片空白；打印 CSS 对 day 同时设置避免页内拆分和强制下一天另起页。它与 Codex 独立 PDF 的 48 页问题是两条不同证据，但都说明出版 QA 不应缺席。

## Counterargument

Tour Pass 的目标也可以只保持为轻量规划器。让它承担深度研究、编辑和出版，会增加界面复杂度、外部来源维护成本和生成时延；多数短途用户可能只需要一张能走的时间表。

这个反对意见成立。因此建议保留“快速规划”入口，把深度生产做成显式的“旅行手册项目”模式，两者复用 Trip Brief、路线和事实服务，不强迫每次规划都走完整出版流程。

## Conditions

中心论点在以下条件下成立：目标产物需要多轮修改、文化内容、真实图片、预约执行和 PDF/移动端交付；用户把成品当作旅途中反复查看的手册。

如果用户只问两天周末怎么玩、无需保存和打印，现有一次骨架生成加确定性核验更经济，不应强制引入全部生产阶段。

## Unproven

- 新流程能否在可接受的时间和成本内稳定产出 7 日以上手册，尚未实现；当前基准只证明旧流程约 69.8 秒可返回一个未达交付标准的结果。
- 门票、酒店和机票是否能长期获得稳定、合法、可自动化的官方数据源，尚未证明。
- 自动 PDF 分页检查能消灭多少人工目检，尚需用本次成品和更多样本评估。
- 文学风格是否能形成可量化质量门槛，目前仍需要编辑判断。
