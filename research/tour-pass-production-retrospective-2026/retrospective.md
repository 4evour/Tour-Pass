# 从一张行程表到一本旅行手册：Tour Pass 生产流程复盘

## 先说结论

这次真正做出来的，不是一份“天津四天、济南三天”的普通攻略，而是一套三个人能照着走、能查地址、能点导航、知道何时抢票、在路上也愿意翻看的文化旅行手册。

第一处失误发生在动手之前。Codex 没有真正理解你要的产品是什么，直接按普通行程攻略开工，最初的内容结构和页面结构都不合适。随后才开始补夜游、餐饮、逐段交通、地址、图片、预约与购票；HTML 做得能看之后，又遇到手机不方便打开、PDF 折叠内容丢失、链接在微信预览里失效、48 页太长、图片和段落断得难看。直到这一步，生产目标才被逐步校正成“能执行、有人文内容、适合手机和 PDF 的旅行手册”。

现有 Tour Pass 已用同一需求完成一次基准运行。它确实具备结构化约束、模型排程、高德、版本、分享与浏览器打印的骨架，但实测也确认：长输出会截断，紧凑重试与自动修复会继续压缩需求，分组返程无法表达，铁路没有进入 evaluator，预约任务不可执行，完整度会误判，PDF 的 day 分页规则会制造大面积空白。详细证据见 `baseline-run-report.md`。

因此建议保留当前“快速规划”模式，同时新增“旅行手册项目”模式。前者几分钟给出能走的方案；后者允许用户和系统一起把方案做成成品。

## 一、这次到底生产了什么

最终交付有两个方向。

- 实用版把地址、逐段路线、交通时间、餐饮、预约和行李提醒集中起来，压到 28 页。
- 人文版保留实用信息，又补了城市叙事、文学引文、《潜伏》剧情线、真实图片与出处，控制在 30 页。

这两个版本没有互相覆盖。这个选择是对的：实用信息追求扫一眼就能执行，人文内容需要停下来读。把它们强塞进同一个密度和版式，结果往往是导航不够快，文章也读不舒服。

成品之外，还留下了手机 HTML、真人导游手册 Markdown、两套 Playwright 导出脚本、PDF 页图和 contact sheet。问题是，这些东西都散落在 Tour Pass 正式模型之外。下次换一座城市，很多步骤还得重新想。

## 二、需求发现：不是用户没说清，而是 Codex 没先定义产品

### 实际过程

第一轮已经有不少硬条件：三人同行、广州与北京分别出发、天津酒店已订、10 月 3 日转济南、10 月 6 日返程、两个方向分别回北京和广州、房型与预算、偏文化、要博物馆和《潜伏》地点。这些信息足以判断它不是一张简单清单，至少需要处理多人分流、长假交通、文化专题和执行细节。

后续要求确实是在看到初稿后继续明确的：别处处说“未核实”；行程可以到晚上 11 点；没必要每天早起；要吃什么也得说；每天不能套同一模板；景点讲解要更详细、更文学；每个地点要地址、交通和图片；PDF 要在手机看；购票链接最好一步直达。但这不能替第一版开脱。Codex 应该在开工前追问成品形态和使用场景，或先给出一页样张验证理解，而不是先生产完整的错误架构。

### 踩坑

初期把硬约束当成了全部需求，又自行选择了普通攻略的表达架构。结果不只是文案不够好，连生产架构都错了：每天套统一模板，地点讲解与交通割裂，地址另设一张表，票务放在后面补，网页交互和 PDF 交付也没有同时设计。

| 错误层次 | 最初做法 | 为什么不合适 |
|---|---|---|
| 产品理解 | 把任务当成常规多日攻略 | 用户要的是能在国庆现场执行、又愿意阅读的人文手册 |
| 内容架构 | 每天重复固定餐次与时段模板 | 旅行节奏应由当天主题、开馆和夜游决定 |
| 信息架构 | 景点、地址和交通分区呈现 | 现场需要沿一条路线连续读取 |
| 事实架构 | 预约、票价和链接写进散文或后补 | 易变事实无法单独刷新，也不容易检查遗漏 |
| 交付架构 | 先按交互 HTML 设计，后来再适配 PDF | 折叠、勾选和吸顶导航在 PDF 中天然失效 |
| 版本架构 | 直接在成品文件上持续叠加 | 难以知道哪次修改影响了内容、事实还是版式 |

### 当时怎么修

每次用户指出不对，就在现有成品上加一个层次：从时间表到导游口吻，从地点到路线，从路线到地址，从地址到导航，再从导航到票务和 PDF。这种修法最终能做出成品，却让前面的错误结构一路带到后面，返工代价越来越高。

### 应沉淀的能力

创建项目时先产出一份 Trip Brief，不急着生成全文。除了旅行约束，它至少要记录：

- 交付形态：网页、手机长图、PDF，还是三者都要。
- 内容层级：快速攻略、可执行手册、人文导览。
- 文风：简洁、导游式、文学性，以及允许引用的程度。
- 专题线：如《潜伏》，是否需要剧情、取景、历史原型，是否介意剧透。
- 使用场景：行前研究、旅途中查阅、打印留存。
- 验收项：每站地址、每段交通、每个预约入口、图片覆盖率、页数目标。

Brief 允许“不确定”，但不确定项必须是显眼的待决定事项，不能藏在长对话里。

## 三、约束建模：三个人并不总是一支队伍

### 实际过程

这次行程有一个很典型的结构：天津和济南阶段三人同行，返程却分流，一人去北京，两人去广州；两位女生先从广州到天津，另一人 10 月 1 日从北京加入。住宿又有一间双床房和一间大床房，以及分房预算。

### 踩坑

传统 `party + arrival + departure` 很容易把全队当成一条共同路线。返程如果只存一个 departure，就只能靠备注描述另一组人的方案。房型也不是一句“3 人 2 间”就够，还涉及每间价格上限。

### 当时怎么修

在导览中用自然语言和多套返程方案表达，没有回写成 Tour Pass 可计算的数据。

### 应沉淀的能力

把交通段建模到 traveller group：

```text
TravellerGroup A：2 人，广州出发，10/6 回广州
TravellerGroup B：1 人，北京出发，10/6 回北京
Shared Segment：天津 10/1–10/3，济南 10/3–10/6
Room A：双床，≤400 元/晚
Room B：大床，≤300 元/晚
```

这样 12306、机票、行李和接送建议才能按人群生成，不会在一条全队 departure 上打补丁。

## 四、路线规划：从“列景点”变成“每一段怎么走”

### 实际过程

初稿先安排日主题和景点。用户随后要求每个地点之间都写公共交通与打车耗时，又把“今日地址簿 + 交通表”改成一条纵向路线：站点是地点，站点之间是移动方式与预计时间，点站名直接打开高德。

这次改动很重要。旅途中需要回答的是“我现在在哪里，下一站去哪，怎么去，几点到”，不是回到另一张表里找地址。

### 踩坑

- 地址、交通和正文分散，读者要来回对照。
- 只写地铁几号线不够，步行进出站、等车和国庆拥堵都会吃掉时间。
- 高德坐标能证明地图位置，却不能说明排队、安检和景区内部步行。
- 线路表适合电脑横向看，不适合手机窄屏和 PDF。

### 当时怎么修

每一天改成线性 journey：地点节点可点，节点间写步行、地铁或打车基准时间，再补国庆执行余量。取消重复地址簿。

### 应沉淀的能力

用 Route Graph 取代把 transfer 塞在日程文字里。节点保存地点身份、地址和入口；边保存模式、基准耗时、步行距离、换乘数、查询时间和缓冲策略。同一条边可以有公交和打车两个方案，但界面只默认展示当前最合适的一个。

路线 QA 还应检查：是否闭合到酒店、是否跨城后留出进出站时间、是否出现同一区域折返、轻松节奏下连续步行是否过长。

## 五、餐饮：不能只写“附近解决”

### 实际过程

用户直接指出“去吃什么特色餐饮也没有做推荐”。后来才补上天津菜、早餐、小吃、济南鲁菜与泉水相关餐饮，并把用餐位置跟当天路线绑在一起。

### 踩坑

“在景区附近午餐”对排时间有帮助，对游客几乎没有决策价值。反过来，随手编一家店又可能地址不对、排队太久或已经停业。当前 Tour Pass 的餐饮选项虽然能绑定高德地点，但单人价格默认空，营业和排队也没有稳定来源。

### 当时怎么修

优先推荐“菜 + 片区 + 一到两个可核对店铺”，并把主选和备选放在当天路线附近。没有足够证据时，不强行写精确人均。

### 应沉淀的能力

Dining Dossier 至少需要招牌菜、适合餐次、客单价区间、地址、营业时间来源、排队风险、预约入口、与前后站的距离。展示时先告诉用户吃什么和为什么顺路，店铺是执行选项，不让店名盖过旅行本身。

## 六、人文写作：文学感不能靠堆形容词

### 实际过程

内容经历了三次明显转向：先从表格说明改成真人导游口吻，再把景点介绍扩充，最后加入文学引文、城市气质和《潜伏》线。

天津的叙事逐渐围绕建筑与时代展开：会馆、租界建筑、饭店、海河和隐蔽战线。济南则跟着水走，从趵突泉、黑虎泉、曲水亭街到大明湖，让路线本身承担城市解释。

### 踩坑

- 初稿“正确但没味道”，每站只是推荐理由。
- 为了显得有文化，容易堆年代、典故和空泛抒情。
- 文学句子写得漂亮，不代表事实可靠。
- 一段讲解既要在手机上读得下，又要在 PDF 里不占掉半页。

### 当时怎么修

先查官方文旅、馆方和地方政府资料，再用文学语言重写；引文注明作者与篇名。每段尽量包含“眼前看什么、它为何重要、怎么走或怎么停留”三个层次，少写悬空评价。

### 应沉淀的能力

Content Dossier 应把研究材料和最终文案分开：

- `facts`：时间、人物、建筑、事件和来源。
- `viewing_cues`：到现场先看什么、站在哪里看。
- `interpretation`：编辑允许的解释，标注推断强度。
- `quotes`：原文、作者、作品、版权状态。
- `variants`：卡片短版、导游版、长文版。
- `approval`：事实审阅与文风审阅状态。

模型可以写得漂亮，但只能在 Dossier 的事实边界内写。

## 七、《潜伏》专题：兴趣标签不够用

### 实际过程

最初“潜伏”只是用户兴趣和若干打卡点。后来用户明确要求：遇到相关景点，都要写电视剧中的情节。于是内容不再只是“这里拍过”，而是要解释剧情中的空间、人物关系、镜头记忆，以及现实建筑与故事之间的边界。

新华路 31 号的军统天津站旧址也在后期追加。这个例子说明，专题旅行的地点清单会随着用户记忆不断生长，不能把第一版 must-visits 当作最终全集。

### 踩坑

影视迷最在意的恰恰是普通攻略会略过的细节。更危险的是三种关系容易混在一起：真实取景地、剧情中的地点、与时代背景有关但未在剧中出现的建筑。混写会制造很有感染力的错误。

### 当时怎么修

用更谨慎的层次叙述剧情、建筑空间和历史背景，不把所有相关建筑都说成已确认取景地。

### 应沉淀的能力

新增 Theme Thread，节点不是普通标签，而是带证据类型的关系：

```text
confirmed_filming：有可靠来源确认取景
on_screen_identity：剧中被当成什么地点
historical_context：与真实历史背景有关
visual_echo：只有空间气质相似，不声称取景
```

专题还要存剧集、集数或情节范围、人物、剧透级别和来源。用户可以选择“轻度彩蛋”或“影迷深度线”。

## 八、图片：宁缺毋滥仍然需要资产管理

### 实际过程

用户先要求更多精品图，后来明确“每个景点最好都有；没有高质量的就算了”。最终人文版运行时生成 29 张图片，并在图下注明来源、作者与许可；导出脚本会滚动页面触发懒加载，再等待图片解码。

### 踩坑

- “每站一图”和“只要高质量”会冲突。
- 远程图片在浏览器能显示，导出时可能还没加载或已经失效。
- 横图在手机和 A4 上需要不同裁切；强行固定高度会切掉主体。
- 图片来源写在正文里，不能被程序检查是否缺作者或许可。

### 当时怎么修

选用有明确许可的 Wikimedia Commons 实景图；导出前把图片改为 eager，逐页滚动并等待 `decode()`；打印样式取消固定裁切，限制最大高度。

### 应沉淀的能力

Asset Manifest 记录 URL、本地缓存、作者、许可、来源页、拍摄对象、焦点、推荐比例、alt、使用位置和加载状态。没有通过来源和清晰度门槛的地点，可以没有图，界面不应留下空框。

## 九、预约与购票：从“需要预约”到“现在能做什么”

### 实际过程

用户连续两次强调：所有需要提前预约、抢票的项目都要说明。后续又要求正确购买链接，不想自己逐个搜索。最终页面加入开售日历、优先级、价格、证件、操作入口、没抢到怎么办，以及铁路、博物馆、摩天轮、相声和景区的不同规则。

### 踩坑

- “需预约”没有时间和入口，等于没说。
- 有的官方入口只有微信公众号或小程序，PDF 无法直接跳到下单页。
- 门票规则、价格和开窗周期都会变，必须保存核验日期。
- 第三方购票页能直接打开，但不等于官方；免费博物馆尤其不能暗示付费代约。
- 12306 能查时刻和参考票价，不代表接入了余票。

### 当时怎么修

把任务按日期排成操作日历；能给网页入口的直接给，微信专用的明确写公众号/小程序名称和操作路径；为售罄、天气和限流提供替代方案。

### 应沉淀的能力

Booking Task 不应再只有 `status` 和一句 action。至少需要：

```text
target / visit_date / priority
release_rule / computed_open_at / deadline
price / price_scope / fee_note
official_channel / booking_url / fallback_url
identity_documents / baggage_rules
last_verified_at / valid_for / evidence_refs
failure_fallback / owner / completion_state
```

系统可以计算“9 月 22 日 14:15 抢 10 月 6 日票”，但必须把计算依据和时区保存下来。到期前提醒，过了有效期就标红要求复核。

## 十、HTML 交互与手机使用：一个链接不等于可到达

### 实际过程

HTML 中有日期导航、折叠区、勾选记忆和高德跳转，在电脑浏览器里体验不错。手机直接打开本地 HTML 不方便，于是转 PDF。PDF 保留普通链接，却失去了折叠、勾选和吸顶导航。

后来又发现：地址链接在电脑 PDF 阅读器里可以打开，手机微信预览点击却没反应。页面只好增加提示，让用户改用 WPS、Adobe Acrobat 或系统文件应用。

### 踩坑

这里有三层兼容性：PDF 是否保存链接注释、阅读器是否允许外部 HTTPS、浏览器是否允许网页唤起高德 App。任何一层拦截，用户看到的都是“点了没反应”。

### 当时怎么修

PDF 中保留 HTTPS 高德 URI，并写明替代阅读器。这个修法能绕过部分问题，但还不是产品级方案。

### 应沉淀的能力

每个地点提供四种出口：普通 HTTPS 页面、地图 App 唤起、可复制的完整地址、二维码。网页按设备优先唤起 App，失败回退到 HTTPS；PDF 默认展示 HTTPS 链接和二维码，不把成功寄托在一个深链上。发布 QA 必须覆盖微信预览、WPS、Acrobat、iOS 文件和 Android 系统阅读器。

## 十一、本次独立 PDF 的教训：不能直接算在 Tour Pass 头上

### 实际过程

第一次把所有折叠内容展开导出后，PDF 达到 48 页。用户指出了大量空白、图片和段落被难看切开的页面。随后调整字体、边距、组件间距和分页规则，删掉重复呈现，不删核心行程；实用版压到 28 页。人文版内容更长，但通过独立排版控制在 30 页。

这里仍需划清边界：48 页版本是 Codex 为独立 HTML 写导出脚本生成的，不能倒算成 Tour Pass 的缺陷。后续基准已经把 Tour Pass 的真实 `response.json` 注入当前 `renderPlan()`，它得到的是另一份 21 页 PDF；这份 PDF 也有明显空白，但成因可直接落到 Tour Pass 的 day 分页规则。两套结果应分别记录，不用一个替代另一个。

### 踩坑

网页组件常用 `break-inside: avoid` 保持卡片完整。打印时，如果一张卡片放不进当前页，浏览器会把整张推到下一页，前一页就剩下一大片空白。若卡片本身接近或超过一页，又可能被强行切开。图片固定高度和正文不可拆规则叠加，结果更糟。

### 当时怎么修

- 对短小单元保留 `break-inside: avoid`，长正文允许分页。
- 标题 `break-after: avoid`，正文使用 orphans/widows 减少孤行。
- 图片在打印中用自然高度并设置最大高度。
- 把重复地址簿、重复说明和装饰间距压缩。
- 先生成每页截图和 contact sheet，再目检全册，而不是只看第一页。

### 应沉淀的能力

这段经验已经完成第一步回灌：同一份需求已生成 Tour Pass 基准 PDF，并确认当前分页规则会制造空白。下一步应做 CSS A/B，而不是凭感觉缩小字体：允许长 day 跨页，短 stop 保持完整，再比较空白率、标题孤悬和段落切分。Publication Model 仍应把网页组件和打印组件区分开；导出流程固定为冻结数据版本、展开打印内容、等待字体与图片、生成 PDF、渲染页图、运行自动检查、人工抽查、发布。

QA Report 至少检查：页数、空白率、元素溢出、图片加载失败、图片过度裁切、标题孤悬、链接数量、外部链接状态、书签、字体嵌入和文件大小。自动检查不能判断文学质量，但可以把 30 页目检缩小到几个高风险页面。

## 十二、补跑 Tour Pass 后看到了什么

最初生产确实没有使用 Tour Pass；这也是为什么早先不能把独立 HTML/PDF 的问题归因于产品。复盘阶段已经补做了同一需求的 Tour Pass live 基准，因此现在可以比较“现有链路会保留什么、会丢掉什么”，但仍不能把两个成品当成同一模板的 A/B。

基准使用完整结构化请求运行 69.8 秒。第一次模型输出打满 8,192 tokens 并截断，第二次紧凑重试成功；随后 21 次自动修复删除了 6 个执行或夜游节点。最终 35 个日程项只有 8 个绑定实体，开放核验为 0，天津到济南还被错误修成 flight，但 Hard Validator 仍通过、完整度仍为 84。

前端基准导出为 21 页。页面没有横向溢出，却没有图片和购票链接，5 个折叠区默认关闭；PDF contact sheet 显示多页大面积空白。现在可以确认，Tour Pass 不只是缺少后半程研究对象，现有前半程在复杂长行程上也有需求保真与评分可信度问题。

Codex 能继续做，是因为它可以在同一工作区里读对话、查资料、直接编辑 HTML/CSS、运行浏览器、看截图、改导出脚本，再生成一次。代价是流程没有结构化，很多判断留在人和对话里，成品也没有进入 Tour Pass 的版本体系。

因此这次复盘先承认 Codex 的需求理解失误，再用基准运行验证 Tour Pass 的真实边界。下一步优先修 traveller-group、leg 级交通偏好、紧凑重试保真、rail evaluator、完整度门槛和 PDF 分页；之后再把 Content Dossier、Theme Thread、Asset Manifest 与 Publication Model 补成正式对象。

## 十三、建议的新生产流程

### 1. 建立 Trip Brief

系统整理已确认约束、待决定项、同行人分组、交付渠道和验收标准。用户只审一页摘要。硬冲突在这里解决。

### 2. 生成候选行程骨架

继续复用当前单次模型 Schema 和 repair 机制。输出先不追求文学，只保证城市、日期、片区、主线和体力合理。

### 3. 构建 Fact Ledger

地点、路线、开放、门票、预约、车次、酒店和餐饮分别查询。每条事实带来源、抓取时间、有效期、适用日期和置信度。无法证明的内容留空，不用“未核实”淹没正文，而是在任务面板集中处理。

### 4. 编译 Route Graph

根据真实节点与边生成每天的顺序、时间和备选交通。这里才写入“地铁约多久、打车约多久”和节假日缓冲。

### 5. 建立 Content Dossier 与 Theme Thread

只为重点景点做深度研究；普通站点保持短讲解。专题线跨天连接地点，避免每天重复介绍《潜伏》。事实审核后再生成导游短版和人文长版。

### 6. 建立 Asset Manifest

按地点挑图，检查来源、许可、尺寸和主体。宁可缺图，也不放模糊或来历不明的图。下载或缓存策略在发布前确定。

### 7. 生成 Publication Model

把相同内容编译成网页、PDF 和手机简版。决定模块顺序、折叠状态、图片版式、页数目标、导航降级和二维码，而不是直接拼 HTML 字符串。

### 8. 执行 QA Gate

先跑行程硬校验，再跑事实新鲜度、资产完整性、链接与版式检查。系统生成 contact sheet，把高风险页面交给人看。只有通过目标渠道验收的版本才能发布。

### 9. 旅行前刷新

出发前 7 天和 24 小时只刷新易变事实：天气、开放公告、票务状态、列车和道路。不重写已经批准的人文内容和整本排版。

## 十四、建议的数据对象

| Object | Responsibility | Key output |
|---|---|---|
| Trip Brief | 保存人、日期、预算、节奏、主题、渠道和验收目标 | 一页可确认需求摘要 |
| Fact Ledger | 保存带来源、有效期和状态的原子事实 | 可更新、可追责的事实表 |
| Route Graph | 保存地点节点和多模式交通边 | 可计算时间轴与导航 |
| Content Dossier | 保存景点资料、观看线索、引文和文案版本 | 短讲解与长讲解 |
| Theme Thread | 保存影视、文学、建筑等跨地点关系 | 专题叙事线 |
| Asset Manifest | 保存图片、许可、焦点、裁切和加载状态 | 网页/PDF 可复用资产 |
| Publication Model | 保存渠道结构、模块、样式和分页意图 | HTML、PDF、长图 |
| QA Report | 保存语义、事实、资产、链接和页面检查 | 是否可发布及问题列表 |

这些对象不要求一步全部做完。它们先把这次散在对话和 HTML 里的信息找到归宿。

## 十五、开发路线图

### P0：先让下一次真的少返工

1. 新增 `TripProject` 与 Trip Brief，把成品类型、文风、专题和验收项纳入项目。
2. 扩展 traveller group、room requirement 和分流交通段。
3. 把逐段 route、地址、导航和节假日缓冲做成正式字段。
4. 扩展 Booking Task：开窗、截止、价格、入口、证件、行李、来源与复核时间。
5. 支持字段级 patch 和区块 diff，用户只改某一天时不重写全篇。
6. 先用本次内容建立 Tour Pass PDF 基线；根据实测结果补自动展开、图片等待、页图、链接统计和基础分页报告。
7. 为地图链接加入 HTTPS、复制地址与二维码降级。

P0 的验收标准不是“按钮能点”，而是用这次天津济南 Brief 重新生成：人工不直接改 HTML，也能得到地址完整、预约可执行、手机可导航且没有明显空白/裁切的 PDF。

### P1：研究与编辑工作台

1. 上线 Fact Ledger、Content Dossier 和来源审阅。
2. 上线 Theme Thread，支持影视取景、文学和建筑专题。
3. 上线 Asset Manifest 与许可检查。
4. 浏览器批注锚定到日、站点、段落、图片或页面，并自动生成编辑任务。
5. 支持实用版、人文版从同一项目分支发布，公用事实而不互相覆盖。

### P2：出版与自动验收

1. 服务端 HTML/PDF/长图渲染，保存 renderer 版本。
2. 自动检查空白率、溢出、孤行、图片失败、链接、文件大小和书签。
3. 建立移动端链接兼容矩阵和回归测试。
4. 对票务、天气、交通等易变事实做定时刷新和到期提醒。
5. 用真实项目建立评测集，比较首版通过率、人工修改次数、事实过期率和发布耗时。

## 十六、下一次应该怎样做

下次面对类似请求，第一轮不要急着写七天全文。先交付 Trip Brief、路线主线和一页样张：选一天做完整的导游文字、路线、图片和票务模块，让用户确认密度与风格。样张通过后再批量生产其余日期。

事实与文字分开走。地址、开放、票价和购票入口进 Fact Ledger；导游讲解从已批准事实生成。路线变化时只重新编译受影响的时间轴，文学段落不跟着重写。图片和 PDF 最后接入，但它们的验收标准要在第一天就写进 Brief。

这会少走很多弯路。不是因为减少沟通，而是因为每次沟通都会落到一个明确对象上：用户改的是约束、事实、路线、文案、图片还是版式。Tour Pass 也能从“每次重新生成一份答案”，变成“把一个旅行项目逐步做完”。
